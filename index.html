Dependency Preservation, explained

1 · The big idea

When we normalize a database we split one big relation R into smaller fragments R1, R2, … Rn to remove redundancy. The rules of the data (its functional dependencies, F) must still be enforceable afterwards.

A decomposition is dependency-preserving if every dependency in F can be checked by looking at one fragment at a time: no expensive join is needed just to validate an insert or update.

(F₁ ∪ F₂ ∪ … ∪ Fₙ)⁺ = F⁺    where Fᵢ = FDs of F⁺ whose attributes all lie inside Rᵢ

2 · Key terms

Functional dependency X → Y
Whenever two rows agree on X they must agree on Y. Example: Zip → City.
Closure X⁺
Every attribute you can reach starting from X by repeatedly applying FDs in F.
Projection Fᵢ
The dependencies that can be stated using only the attributes of fragment Rᵢ.
F⁺
The set of all dependencies implied by F (Armstrong's axioms).

3 · How to test it (the algorithm used by this tool)

Computing every Fᵢ is expensive. Beeri & Honeyman gave a shortcut that never builds F⁺. For each dependency X → Y in F:

  1. Start with Z = X.
  2. For every fragment Rᵢ, update Z = Z ∪ ((Z ∩ Rᵢ)⁺ ∩ Rᵢ). The closure is taken with respect to the original F.
  3. Repeat step 2 until Z stops growing.
  4. If Y ⊆ Z the dependency is preserved; otherwise it is lost.

The decomposition is dependency-preserving only when every dependency in F passes. The Trace Player in the Analyzer animates exactly these steps.

4 · Worked example

R(A, B, C), F = { A → B, B → C }, decomposed into R1(A, C) and R2(B, C).

  • B → C: Z = {B}. R2: {B}⁺ ∩ R2 = {B, C} → Z = {B, C} ⊇ {C}. ✓ preserved (lives inside R2).
  • A → B: Z = {A}. R1: {A}⁺ = {A, B, C}, ∩ R1 = {A, C} → Z = {A, C}. R2: Z ∩ R2 = {C}, {C}⁺ = {C} → nothing new. Z = {A, C} ∌ B. ✗ lost.

Result: not dependency-preserving. Fix by keeping A, B together, e.g. R1(A, B), R2(B, C).

5 · Why it matters

  • A good decomposition should be lossless-join, dependency-preserving and have fragments in a good normal form.
  • You can always get lossless + dependency-preserving with 3NF synthesis. BCNF guarantees lossless but sometimes must give up a dependency (the “postal address” preset shows this).
  • A lost dependency means the DBMS needs a join (or an application check / trigger) to enforce that rule.
Remember: lossless-join answers “can I rebuild the data?”, dependency preservation answers “can I still enforce the rules cheaply?”. They are independent: you can have one without the other.

    Help · user manual

    How to use this website

    What does it do?

    You give it a relation R, a set of functional dependencies F and a proposed decomposition. It tells you, dependency by dependency, whether each rule can still be enforced inside a single fragment, shows how it worked that out, and suggests a repair if something was lost.

    Step by step

    1. Open the Analyzer tab. Optionally pick an example from the drop-down. It fills all three boxes for you.
    2. Attributes of R. Type the column names. Use single letters with no spaces (ABCD) or separate longer names with commas (City, Street, Zip). Tiles appear below to confirm what was understood.
    3. Functional dependencies. One per line using -> or →. Left and right sides may list several attributes: A, B -> C, D (or AB -> CD with single-letter names).
    4. Decomposition. One fragment per line. Name it R1(A, B) or just list the attributes. Every attribute of R must appear in at least one fragment.
    5. Press Analyze ▶. Results appear on the right (below on phones).
    6. Read the verdict, then explore the other result cards using the “Jump to” buttons.
    7. Press ⬇ Download in the top bar to save a full report as PDF, Word or text.

    What each control does

    • Analyze ▶: validates inputs and runs the analysis.
    • Clear: empties all inputs and results.
    • 🔗 Copy share link: copies a link that reopens this exact problem for a friend or lecturer.
    • Trace Player (◀ Next ▶ Play): steps through how the set Z grows for one dependency. Click a dependency button to switch.
    • Apply suggestion (in the Repair card): adds the suggested fragments to your decomposition and re-runs the analysis.
    • ☀️ Day / 🌙 Night: switches the colour theme.
    • ♿ Accessibility: bigger text, high contrast, easy-read font, reduced animation.
    • Self-test (bottom of Analyzer): runs built-in checks on the engine.

    The Play tab (games)

    • Spot the Lost FD: a random design appears. Decide whether the highlighted dependency is preserved (Yes / No). You get an explanation, and can replay it in the Analyzer's Trace Player.
    • Fragment Builder: tap attribute tiles to place them in fragments. Cover every attribute, respect the size limit and keep every dependency ✓. Submit to earn up to 3 stars (preserved, lossless, BCNF).
    • Concept Quiz: 8 multiple-choice questions in random order.
    • XP, level, streak and badges are saved in your browser.

    The COMPETITIVE EXAM section

    1. Press the orange COMPETITIVE EXAM button at the top of any page.
    2. Every question shows its type (MCQ, MSQ or NAT), difficulty, topic and a tag. ✔ Past paper tags give the exam and year. ✎ Practice questions are original and carry no year.
    3. Use Find questions to filter by source, exam, topic, type and difficulty, or to search for a word.
    4. Study mode shows the correct answer and a step-by-step solution under every question.
    5. Practice mode hides them. Pick an option (or type a number for NAT questions), then read the solution. A first-time correct answer earns 5 XP in the Play tab's level system.
    6. 🔬 Try this in the Analyzer loads the question's relation and dependencies into the Analyzer so you can watch the trace.
    7. Download all saves the whole question bank as text or Word. Print / Save as PDF uses your browser's print dialog.

    The Dashboard

    • The Dashboard is the home page. The six tiles at the top summarise your current analysis (attributes, dependencies, fragments, score, lossless join, keys).
    • The workflow row shows the five steps (Upload, Discover, Analyze, SQL Lab, Play) with a ✓ when you have done each. Click any step to jump to it.
    • Quick start loads an example or a sample dataset in one click.
    • Current analysis shows the verdict, every dependency and a small dependency map. Your progress shows level, XP, streak and badges. Recent activity lists what you did lately.
    • Engine health re-runs the built-in self-tests whenever you press Run again.
    • The small breadcrumb at the top of each workspace tab (Dashboard › Upload › Analyzer › SQL Lab › Play) lets you move along the workflow. On a phone, use ☰ Menu for Help, Developed By, Download and settings.

    The Upload & Discover tab

    1. Drop a file (CSV, TSV, TXT, JSON, Excel) or paste a table whose first line is the column names. Or press a sample button to see it work immediately.
    2. Check the preview and the column list. Tick the columns to analyze (up to 12). Constant columns are skipped automatically.
    3. Choose the largest left side to try, and optionally tolerate dirty data so that a rule with a few typos is still found. Press Discover dependencies.
    4. Read each dependency's evidence. Untick any that look like coincidence, because data can only suggest rules. For rules with violations, show lists the offending rows.
    5. Pick 3NF synthesis (always preserving and lossless) or BCNF decomposition (may lose a dependency), then press Send to Analyzer. Or open the SQL Lab, which can then load your real rows.

    Word and PDF files cannot be read directly: copy the table and paste it into the box, or save it as CSV/Excel first.

    The SQL Lab tab

    1. Set up a problem in the Analyzer, then open SQL Lab and press Build database (needs internet once, to load the SQLite engine).
    2. Read the generated SQL, and look at the tables: the original relation R and one table per fragment. “Joined back” shows whether joining the fragments recreates R (extra rows mean a lossy join).
    3. Choose a dependency and press Insert a rule-breaking row. The row is offered to the original table and then to each fragment table.
    4. ⛔ Rejected means a local rule caught it. ☠ Silent corruption means every fragment accepted its piece but the joined data now breaks the dependency. That is exactly what a lost dependency costs.
    5. Copy SQL / Download .sql give you the full script to run in any SQLite tool.

    How the processing works

    1. Your text is parsed and checked (unknown attributes, missing arrows, uncovered attributes are reported).
    2. For every dependency X → Y the tool grows Z from X using each fragment's closure (see Learn) until nothing changes.
    3. It also projects F onto each fragment, finds candidate keys, a canonical cover, tests lossless join with a tableau (chase) and checks BCNF per fragment.

    How to read the output

    • ✓ Preserved: that dependency can be enforced inside the fragments.
    • ✗ Lost: it cannot; “missing” lists attributes that Z could not reach.
    • Ring score: preserved dependencies out of all dependencies.
    • Dependency map: attributes are nodes; each dependency is a hub “fN” with arrows. Solid line = preserved, dashed = lost. “R1 R2” beside an attribute lists the fragments containing it.
    • Lossless join: the tableau is the table used for the chase test. A row of all as means the join is lossless.
    • Repair: extra fragments that would make the decomposition dependency-preserving.

    Common messages

    • “unknown attribute”: a name in F or in a fragment isn't listed in R. Check spelling (not case-sensitive).
    • “should look like X -> Y”: a dependency line is missing its arrow or has two arrows.
    • “not in any fragment”: your decomposition leaves out part of R.
    • Maximum 12 attributes.
